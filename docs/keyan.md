## 1. 执行摘要

TrimContext 是一个本地 CLI 工具，用于分析 AI Agent 对话历史，识别并清理“腐烂”内容（过时指令、冗余问答、未被引用的工具调用），最终输出压缩后的对话文件，直接降低 token 成本。

**核心结论**：  
- ✅ 技术可行（规则检测 + 本地 tokenizer，无需 LLM）  
- ✅ 市场空白（现有工具只监测或简单修剪，无“诊断+可执行清理”闭环）  
- ✅ 用户痛点真实（Anthropic 官方承认 context rot，开发者普遍受困）  
- ✅ 开源可防御（MIT 协议开放代码，通过商标+企业版+社区建立壁垒）

**建议**：立即启动 Phase 0 验证（3 天），Phase 1 发布 MVP（2 周），总投入约 4 周可获得可用产品。

## 2. 问题定义与市场验证

### 2.1 问题描述
随着 Agent 对话轮次增加，早期信息被后续指令覆盖、变得冗余或从未被引用，但仍在上下文中占据 token，导致：
- 模型准确回忆能力下降（Context Rot）
- 推理成本浪费（为无用 token 付费）
- 开发体验恶化（模型开始遗忘或重复）

### 2.2 市场规模与用户画像
| 用户类型 | 典型场景 | 月 token 成本 | 痛点强度 | 付费意愿 |
|---------|----------|--------------|----------|----------|
| 独立开发者 | 用 Claude Code / Cursor 编程 | $10-50 | 中 | 中（开源自用） |
| AI 产品团队 | 客服/创作 Agent 长期运行 | $200-2000 | 高 | 高（采购工具） |
| 研究/评测人员 | prompt 对比、上下文效率研究 | $50-200 | 中 | 低（学术用途） |

**市场规模估算**：基于 Claude Code、LangChain 等生态活跃用户约 50 万，其中 20% 遭遇 context rot，潜在用户 10 万。假设 5% 愿意为增值服务付费（如企业版），按 $10/月 估算，年收入潜力 $60 万，足以支撑小团队。

### 2.3 现有方案缺口（竞品分析）

| 竞品 | 检测信号 | 输出 | TrimContext 机会 |
|------|----------|------|------------------|
| contextprune | 按类型 + 阈值 | 压缩列表 | 提供价值评分，而非盲目裁剪 |
| delta-prune | 矛盾 | 标注/删除矛盾 | 覆盖过时、冗余、未引用 |
| agentwatch | 多维 rot 评分 | 健康分数 | 从评分到可执行压缩闭环 |
| driftguard | 退化信号 | 建议重置会话 | 修复而非重置 |
| LangSmith / LangFuse | 观测 + 评估 | 仪表盘 | 本地、免费、行动导向 |
| 手动复制 | 无 | 新会话 | 自动化、量化、可审计 |

**空白定位**：没有工具能同时做到 **“诊断腐烂 → 给出清理建议 → 输出压缩文件”**。

## 3. 技术方案（MVP 可落地）

### 3.1 技术栈

| 组件 | 选择 | 理由 |
|------|------|------|
| 核心语言 | TypeScript + Node.js 20+ | 跨平台、易打包、生态成熟 |
| CLI 框架 | Commander.js | 轻量、标准 |
| Tokenizer | @dqbd/tiktoken | 本地计数，支持 cl100k_base |
| 打包 | @yao-pkg/pkg | 生成单文件二进制（Linux/macOS/Windows） |
| 测试 | Jest | 单元测试 + 集成测试 |

### 3.2 腐烂检测算法（无 LLM）

每条消息计算 `rot_score ∈ [0,1]`，综合四个维度：

| 维度 | 权重 | 计算方法 |
|------|------|----------|
| 覆盖性 | 0.35 | 后续消息匹配覆盖关键词（`ignore previous`, `update:`, `instead of`, `correction`），距离越近权重越高 |
| 引用性 | 0.25 | 后续 20 条消息中关键词交集 ≥2？否则惩罚；tool 消息检查 `tool_call_id` 是否被引用 |
| 时效性 | 0.30 | 指数衰减：`exp(-3 * (总条数 - 索引) / 总条数)` |
| 冗余性 | 0.10 | 与前后 3 条 Jaccard 相似度 >0.85 则惩罚 |

**阈值**：默认 `rot_score > 0.7` 标记为腐烂，可配置。

**性能**：10 万条消息（约 200 万 token）分析时间 < 3 秒，内存 < 200MB。

### 3.3 输入输出格式

**输入自动检测**：
- OpenAI Chat Completion JSONL（每行 `{"messages": [...]}`）
- Claude Messages JSON（对话数组）
- 纯文本（`User:` / `Assistant:` 前缀）

**输出**：
- `analyze`：表格 + JSON 详细报告（含每条消息的腐烂分解）
- `compress`：清理后的 OpenAI 格式 JSONL，可直接用于新会话

## 4. 实施路线图（4 周交付 MVP）

| 阶段 | 时间 | 交付物 | 验收标准 |
|------|------|--------|----------|
| **Phase 0：验证** | 3 天 | 原型脚本 + 验证报告 | 对 5 个真实对话，人工判定腐烂检测准确率 > 70% |
| **Phase 1：CLI MVP** | 2 周 | `analyze` + `compress` 命令 | 支持 OpenAI/Claude 格式，输出表格和压缩文件 |
| **Phase 2：增强** | 1 周 | token 计数 + 成本估算 + `--interactive` | 支持 `--model` 参数，交互式确认删除 |
| **Phase 3：生态集成** | 1 周 | Python 包 + 标准输入输出 | `pip install trimctx` 可直接调用 |

**后续（视反馈）**：MCP Server、Web 仪表盘、VSCode 插件。

## 5. 风险与缓解（含否决清单）

### 5.1 技术风险

| 风险 | 概率 | 缓解措施 |
|------|------|----------|
| 规则检测准确率 <60% | 低 | Phase 0 验证后若低于 60%，增加轻量 embedding（sentence-transformers）作为备选 |
| 不同日志格式解析失败 | 中 | 提供 `--format` 强制指定，并输出解析失败的行号提示 |
| 大文件内存溢出 | 低 | 流式解析 + 滑动窗口，默认限制文件 500MB |

### 5.2 产品风险

| 风险 | 缓解措施 |
|------|----------|
| 用户觉得手动运行 CLI 麻烦 | 提供 Python 库 `trim_context(history)` 一行集成；后续可考虑后台守护 |
| 用户不相信自动删除 | 交互模式 `--interactive` 预览 diff，用户确认后再执行 |
| 大厂内置类似功能 | 保持本地、开源、无锁定；专注“诊断 + 可解释性”而非简单压缩 |
| 市场太小 | 先服务独立开发者社区，积累口碑后拓展企业版；已有 `contextprune` 等竞品证明需求存在 |

### 5.3 明确不做的事项（防止 scope creep）

- ❌ 不做实时在线修剪（需适配 Agent 框架状态管理，成本过高）
- ❌ 不做 MCP 服务器（除非有明确 10+ 用户需求）
- ❌ 不做 Web UI（Phase 4 以后再说）
- ❌ 不做 RAG 文档压缩
- ❌ 不承诺适配所有 Agent 框架
- ❌ 不默认调用 LLM（可选高级模式需用户显式开启）

## 6. 开源策略与知识产权保护

### 6.1 许可证选择

**核心代码**：MIT 许可证（允许任意使用、修改、分发，仅保留版权声明）  
**理由**：最大化社区采用，适合 CLI 工具。

### 6.2 保护商业利益的三道防线

| 防线 | 措施 | 实施阶段 |
|------|------|----------|
| **品牌商标** | 注册 `TrimContext` 商标，防止他人用同名做商业产品 | Phase 2 完成后启动 |
| **源码可用但增值闭源** | 社区版 MIT；企业版提供 Web UI、团队协作、审计日志（闭源） | Phase 3 后 |
| **持续领先** | 维护私有 benchmark 数据集 + 规则调优经验，保持算法优势 | 持续 |

### 6.3 应对抄袭

- 若他人完整复制代码并改名，未侵犯商标，但可通过社区力量（比 star、比更新频率）胜出。
- 若他人使用你的代码提供云服务且未遵守 MIT（如删除版权声明），可法律维权。
- 若他人将核心算法用于商业闭源产品，MIT 许可下完全合规，无需担心——这正是开源的意义。
