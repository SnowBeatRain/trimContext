# v0.2 CLI 可用性与 Phase 0 验证开发任务计划

## 1. 计划定位

本文档用于描述 trimctx 下一阶段开发任务，不提供实现代码、测试代码或脚手架代码。

计划重点是把需求、边界、验收标准和执行顺序讲清楚，方便后续开发时按项目现有模块边界实现。

## 2. 当前阶段判断

trimctx 当前已经具备 v0.1 核心能力：

- 可以解析 Claude Code JSONL。
- 可以解析 OpenAI JSONL。
- 可以估算 message tokens。
- 已有 safety rules。
- 已有 scorer。
- 已有 JSON report。
- 已有安全压缩副本输出。
- 已有基础测试。

当前主要问题不是核心链路不能跑，而是产品可用性还不够：

- `analyze` 默认输出完整 JSON，不适合真实长会话人工阅读。
- report 缺少聚合层面的 top reasons，用户很难快速判断主要问题来源。
- Phase 0 真实样本验证还不充分。
- 用户仍然需要手动寻找 Claude Code JSONL 文件。
- 缺少本地环境诊断命令。

因此下一阶段应先完成 v0.2 CLI 可用性和 Phase 0 多样本验证，不做 Web UI、MCP、安装器、slash command 或任何实时 hook。

## 3. 总目标

v0.2 的目标是让 trimctx 从“能分析一个指定 JSONL 文件”提升为“真实用户可以舒服地在终端使用”。

完成后，用户应能：

- 对指定 JSONL 文件运行 `analyze`，看到短摘要。
- 在需要机器可读结果时使用 `analyze --json`。
- 使用 `report` 生成完整 JSON 报告。
- 在摘要和报告中看到 top reasons。
- 使用真实 Claude Code 长会话验证规则是否可信。
- 后续可以通过 `sessions` / `latest` 找到本地 Claude Code 会话。
- 后续可以通过 `doctor` 判断环境是否可用。

## 4. 不做范围

本阶段明确不做：

- 不做 Web UI。
- 不做 MCP。
- 不做 Claude Code slash command 安装器。
- 不做 hooks / statusline / watch。
- 不接入 LLM。
- 不接入 embedding。
- 不使用 Python。
- 不使用数据库。
- 不修改原始 JSONL 文件。
- 不追求最大删除率。
- 不自动压缩当前正在使用的会话。

## 5. 核心原则

### 安全优先

trimctx 的第一原则是：宁可少删，也不要误删。

以下规则必须继续成立：

- protected 消息永不删除。
- `compress` 只能删除非 protected 的 `remove_candidate`。
- `keep_protected`、`keep`、`compress_candidate` 都必须保留。
- 所有 `remove_candidate` 必须有 reasons。
- 原始 JSONL 文件永远不被修改。
- 真实样本报告、压缩文件和人工标注不得提交到公开仓库。

### CLI 友好

CLI 默认输出应服务人类阅读，完整 JSON 应服务自动化和审计。

因此：

- `analyze` 默认输出短摘要。
- `analyze --json` 输出完整 JSON。
- `report` 继续生成完整 JSON 文件。
- `compress` 继续只生成新 JSONL 副本。

### 先验证，再扩展

在 Phase 0 多真实样本验证完成前，不应推进安装器、hook、MCP 或 Web UI。

## 6. 任务总览

优先级顺序如下：

1. 改善 `analyze` 默认输出。
2. 增加 `analyze --json`。
3. 增加 top reasons。
4. 补齐 Phase 0 多样本验证。
5. 完成真实样本安全回归验证。
6. 实现 `sessions` / `latest`。
7. 实现 `analyze --latest`。
8. 实现 `doctor`。
9. 同步文档。

## 7. Task 1：`analyze` 默认短摘要

### 目标

让 `analyze <file>` 默认输出适合终端阅读的短摘要，而不是完整 JSON。

### 用户价值

真实 Claude Code 长会话可能包含几百条甚至上千条记录。完整 JSON 会让用户无法快速判断这次分析是否有价值。短摘要应让用户在一个终端屏幕内看到核心结论。

### 输出内容要求

短摘要至少包含：

- 总 messages 数。
- 总 tokens。
- protected messages 数。
- remove candidates 数。
- compress candidates 数。
- 预计节省 tokens。
- 预计节省比例。
- top reasons。
- 下一步建议。

### 下一步建议要求

摘要末尾应提示用户：

- 如需完整审计报告，使用 `report`。
- 如需完整 JSON 输出，使用 `analyze --json`。
- 如需生成安全压缩副本，使用 `compress`。

### 验收标准

- 大文件下默认输出能在一屏内读完。
- 默认输出不包含完整 `messages` 数组。
- 输出字段名称稳定、直观。
- 数字可读，例如大数字应有分隔或清晰格式。
- 对 0 候选、0 token、空文件等情况有合理输出。

## 8. Task 2：`analyze --json`

### 目标

保留当前 `analyze` 输出完整 JSON 的能力，但改为显式参数 `--json`。

### 用户价值

自动化脚本、调试和审计仍然需要完整 JSON。默认短摘要不能牺牲机器可读能力。

### 行为要求

- `analyze <file>` 输出短摘要。
- `analyze <file> --json` 输出完整 JSON。
- `analyze --json` 输出结构应与 `report` 生成的完整报告保持一致。

### 验收标准

- `--json` 输出可以被 JSON parser 直接解析。
- JSON schema version 保持不变，除非有明确迁移说明。
- `report` 命令行为不因该任务改变。

## 9. Task 3：top reasons

### 目标

在 report summary 中增加 top reasons，并在 `analyze` 短摘要中展示。

### 用户价值

用户不应逐条翻阅 message 才知道主要候选原因。top reasons 应帮助用户快速理解：

- 是 recent rule 保护太多。
- 是旧消息过多。
- 是重复解释过多。
- 是低价值 metadata 过多。
- 是 orphan tool result 较多。

### 数据要求

top reasons 应统计所有 analyzed messages 的 reasons。

统计结果应至少包含：

- reason 名称。
- 出现次数。

默认展示数量建议不超过 5 个，避免摘要过长。

### 排序要求

- 优先按次数从高到低排序。
- 次数相同的情况下保持稳定排序。

### 验收标准

- report summary 包含 top reasons。
- `analyze` 短摘要显示 top reasons。
- 所有 reason 名称来自现有 reason 枚举或类型定义。
- 没有 reason 的消息不会污染统计。
- 统计结果与 message reasons 一致。

## 10. Task 4：Phase 0 多样本验证

### 目标

用至少 5 个真实 Claude Code 长会话样本验证 parser、safety、scorer 和 compressor 的可信度。

### 样本类型要求

至少覆盖：

- 功能开发会话。
- Bug 调试会话。
- 重构任务会话。
- 文档或规划会话。
- 长工具调用会话。

### 样本规模要求

总体最低要求：

- 至少 5 个 session。
- 总 messages 不少于 600。
- 总 tokens 不少于 200k。
- 至少 1 个 session 包含大量 tool_result。
- 至少 1 个 session 发生过 compact。
- 至少 1 个 session 包含用户后续纠正前面需求的情况。

### 数据存放要求

- 原始真实样本放在 `datasets/private/` 或用户本地私有目录。
- 验证输出放在 `tmp-real-validation/`。
- 不把真实 transcript、完整 report、压缩输出提交到仓库。
- 如需公开 fixture，必须先脱敏。

### 人工标注要求

每个样本至少抽样标注以下类别：

- protected。
- keep。
- compress。
- remove。
- unknown。

人工标注用于评估 false deletion 风险，而不是追求删除数量。

### 验收标准

- 5 个真实 Claude Code JSONL 均能成功解析。
- 每个 session 都能生成 report。
- 每条 `remove_candidate` 都有 reasons。
- protected recall 为 100%。
- critical false deletion 为 0。
- parser success rate 不低于 95%。
- remove candidate precision 目标不低于 70%。

### 验证要求

验证前记录原始文件 hash。

验证内容包括：

- `analyze` 可以输出短摘要。
- `analyze --json` 可以输出完整 JSON。
- `report` 可以写入完整 JSON 报告。
- `compress` 可以生成新 JSONL 副本。
- 原始文件 hash 在压缩前后不变。

## 12. Task 6：`sessions`

### 目标

扫描本地 Claude Code transcript 目录，列出最近会话，让用户不必手动寻找 JSONL。

### 用户价值

最终体验要求用户安装一次后，在 AI 内一条命令即可分析当前或最近会话。`sessions` 是进入该体验前的基础能力。

### 扫描范围

Windows 优先支持：

`C:\Users\<user>\.claude\projects\**\*.jsonl`

后续可扩展 macOS / Linux，但本阶段 Windows 是最低验收目标。

### 输出要求

每个 session 至少显示：

- session id 或文件名。
- 所属项目目录。
- JSONL 文件路径。
- 最近修改时间。
- 文件大小。

可选显示：

- 估算消息数。
- 是否可能为 Claude Code 格式。

### 验收标准

- 能列出 Claude Code projects 下的 JSONL。
- 默认按最近修改时间倒序。
- 不读取或输出 transcript 正文。
- 没有 session 时给出清楚提示。
- 目录不可读时给出可理解错误。

## 13. Task 7：`latest`

### 目标

输出最近一个 Claude Code JSONL session 的路径。

### 用户价值

`latest` 是 `analyze --latest` 和后续 `/trimctx` 的基础。

### 行为要求

- 从 `sessions` 的扫描结果中选择最近修改的 JSONL。
- 输出路径应可以直接传给 `analyze`、`report` 或 `compress`。
- 没有可用 session 时应明确提示。

### 验收标准

- 有 session 时输出一个存在的 `.jsonl` 路径。
- 没有 session 时不崩溃，输出明确错误。
- 不修改任何文件。

## 14. Task 8：`analyze --latest`

### 目标

允许用户直接分析最近 Claude Code 会话。

### 行为要求

- `analyze --latest` 等价于对 `latest` 返回的文件运行默认 `analyze`。
- `analyze --latest --json` 输出完整 JSON。
- 同时传入 `<file>` 和 `--latest` 时应报错。
- 未传 `<file>` 且未传 `--latest` 时应报错。

### 验收标准

- 有最新 session 时能输出短摘要。
- `--json` 与指定文件模式保持一致。
- 参数冲突时错误信息清楚。
- 不产生额外文件。

## 15. Task 9：`doctor`

### 目标

提供本地诊断命令，帮助用户判断 trimctx 是否能正常使用。

### 检查项

至少检查：

- Node.js 版本是否满足 Node 20+。
- Claude Code projects 目录是否存在。
- 是否能找到 JSONL session。
- 是否能读取至少一个 session 文件元信息。
- 默认输出目录是否可写。

### 输出要求

输出应面向普通 CLI 用户，避免内部术语过多。

每项检查应给出：

- 状态。
- 简短解释。
- 下一步建议。

### 验收标准

- 环境正常时给出明确通过状态。
- 缺少 Claude Code session 时提示用户可以手动传 JSONL。
- Node 版本不满足时提示升级。
- 写入目录不可用时提示更换输出目录。
- 不读取或打印 transcript 正文。
- 不联网。

## 18. 推荐执行顺序

严格按以下顺序推进：

1. 先做 `analyze` 短摘要和 `--json`。
2. 再做 top reasons。
3. 立刻跑已知真实样本回归。
4. 补齐 Phase 0 多样本验证。
5. 验证规则可信后，再做 `sessions` / `latest`。
6. 再做 `analyze --latest`。
7. 最后做 `doctor`。
8. 每个里程碑完成后同步文档。

不要同时推进太多方向。

## 19. 风险清单

### 风险 1：短摘要隐藏了重要细节

应对：

- 明确提示完整 JSON 路径。
- 保留 `analyze --json`。
- 保留 `report`。

### 风险 2：top reasons 被误解为删除理由排行榜

应对：

- 文档说明 top reasons 是全局原因统计，不等于删除清单。
- 删除仍以每条 message 的 decision 和 reasons 为准。

### 风险 3：真实样本泄露

应对：

- 输出目录固定放入 ignored 目录。
- 不提交真实 report。
- 不提交压缩后的真实 JSONL。
- 公开 fixture 必须脱敏。

### 风险 4：`latest` 选错会话

应对：

- `sessions` 先显示候选列表。
- `latest` 只按明确规则选择最近修改文件。
- 后续再考虑按当前项目过滤。

### 风险 5：规则过于激进

应对：

- Phase 0 验证以 false deletion 为核心指标。
- 不为了节省比例牺牲 protected recall。
- `compress_candidate` 本阶段继续保留，不直接删除。

## 20. 最终验收

v0.2 当前主线完成时，应满足：

- `analyze` 默认适合人工阅读。
- `analyze --json` 保留完整 JSON。
- `report` 仍是完整审计报告。
- summary 有 top reasons。
- `compress` 不修改原始文件。
- protected 消息不会被删除。
- 所有 remove candidates 有 reasons。
- 至少 5 个真实 Claude Code 样本完成 Phase 0 验证。
- Windows 下可以发现 Claude Code sessions。
- `doctor` 可以输出可操作诊断。
- 文档与实际行为一致。
